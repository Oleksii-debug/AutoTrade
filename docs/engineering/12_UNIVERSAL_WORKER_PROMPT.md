# AutoTrade implementation guidelines

Registry and claim records are optional coordination tools for concurrent development. They help identify overlapping work without blocking isolated implementation, testing or integration.

Prioritize the earliest correct delivery of the full product, including financial correctness, execution, continual learning, scientific validation, recovery and accessible Windows and web workflows.

Use `control/INDEX.json` on the default branch for the current product and engineering contracts, work packages, dependencies, findings, qualification evidence and pull requests. The reviewed repository state supersedes older planning snapshots. Record any inaccessible dependency and obtain separate authorization before creating a repository.

There is no global worker, source-worker, auditor or open-PR cap. There is no RED/YELLOW/GREEN admission or numeric capacity gate. Only actual semantic mutation collision and dependency/evidence requirements restrict work. Read-only research and independent audits may proceed concurrently.

First resume useful existing work when that is the highest-value path. Inspect existing PRs/findings to avoid needless duplication, then select the highest-value responsibility you can materially advance. Record advisory scope/ownership metadata when useful, but do not wait for an atomic claim, lease, coordinator, registry service, or unclaimed state before beginning useful isolated work. Existing worker activity is a collision signal, not a prohibition: switch to non-conflicting work or reconcile/rebase when overlap occurs.

Use an isolated worktree/branch and the canonical package PR. Reuse the approved LEAN foundation and provenance-cleared components. Do not copy unclear-license source, sports financial logic, a second OMS, browser trading automation or unfinished application infrastructure. Resolve ordinary implementation details yourself within the approved contracts; a cross-contract change needs an explicit owned migration and affected-consumer review.

Implement the complete claimed responsibility and its meaningful tests. Money uses exact units/decimal contracts; provider acknowledgements are not fills; ambiguous sends require reconciliation; unknown exposure remains reserved; risk and user authority cannot be overridden by strategies/models. Research must remain causal, with complete trial accounting and independent promotion/retention checks. Desktop/web share one state and keyboard/NVDA behavior is a real acceptance requirement. Zero-LLM operation remains useful.

Use safe non-live fixtures/simulators and approved test environments. Development authorization is not authorization to place real trades, withdraw funds, expose credentials or change a user's account. Real execution requires the exact separately configured account/build/policy authority and applicable qualification.

Test the relevant behavior and failure paths; report only tests actually run. Evidence names exact source head, schemas, input hashes, outcomes and limitations. Do not claim economic edge from green CI, a profitable backtest or paper fills. Do not claim NVDA usability from screenshots or an automated scan alone.

Keep repository state current while doing useful work. If a workline is blocked, record the concrete dependency and preserve branch/evidence, then immediately pursue another compatible useful task. Queued/pending CI, another active PR, stale claim metadata, a missing registry service, or an expired lease is never by itself a reason to stop. Stale coordination metadata does not invalidate otherwise correct commits or prohibit merge. Recover and reconcile previous work instead of needlessly duplicating it.

Submit/update the appropriate PR with the problem, changed behavior, scope, tests, provenance, risks and integration target. Resolve actionable review findings. Registry handoff/release metadata is optional coordination state and is never a prerequisite for continuing work or integrating otherwise qualified changes. A draft PR, one successful test or a comment is not a finished package.

After completing a work package, continue with the next compatible priority. Open coordination records only when they support implementation or review. Changes to external launchers are outside this workflow.

Record accepted changes, exact verification evidence, open dependencies and the relevant pull request at the end of each work interval.
