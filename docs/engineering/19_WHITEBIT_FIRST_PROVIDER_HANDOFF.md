# WhiteBIT — перше підключення справжніх ринкових даних

Дата: 17.10.2026. Доповнення до чинних планів AutoTrade, без нового фінансового ядра.

## Фактичний стан

Зареєстрований акаунт не дорівнює виданому API-ключу. У перевірених матеріалах власника знайдено налаштування двофакторної автентифікації; пару API Key/Secret не підтверджено. Секрет Authenticator не є API-ключем. Жодних секретів, адрес проживання, паролів чи контактних даних до GitHub не внесено.

Публічні WhiteBIT REST/WebSocket дані доступні без приватного API-ключа. Це дозволяє розробляти професійний продукт зі справжніми спостереженнями та власним симуляційним виконанням. Не плутати походження даних і середовище виконання. Біржа не отримує симуляційні заявки нашого SimulatedProvider.

Новий код: `research/autotrade_research/integrations/whitebit_public.py`.
Новий інструмент розробника: `tools/probe_whitebit_public.py`.
Тести: `research/tests/test_whitebit_public.py` — 34/34 локальних offline перевірок успішні. Один тест перевіряє форму виклику canonical RawMarketUpdate через явно позначений замінник, а не весь runtime.
Реальний мережевий запуск інструмента завершився `PUBLIC_API_NETWORK_UNAVAILABLE` / exit 2: DNS мережі середовища недоступний. Живий доступ і підключення акаунта НЕ підтверджені.

Код у PR #2393, не у main. Існуючий приватний WhiteBIT адаптер `mvp/autotrade_mvp/whitebit.py` зберігається. Жодного нового приватного відправника заявок.

## Що реалізовано зараз

GET-only клієнт з офіційним зафіксованим доменом, SSL-перевіркою, без ключів, приватних маршрутів, перенаправлень, автоматичних повторів та успадкованих proxy. Обмежені розмір JSON, глибина, кількість рівнів, частота та timeout. Перевіряються назва ринку, точні decimal-рядки, часові мітки, прострочення, порядок і дублікати цін, перехрещений стакан, мінімальні розміри та статус spot-ринку.

Вихід містить bid, ask, обсяги, спред, час джерела, час отримання, digest сирих даних, ознаки `PRODUCTION_PUBLIC` і `SIMULATION_ONLY`. Перетворення в чинний `RawMarketUpdate` вимагає відповідного evidence_ref після реального збереження сирих байтів у канонічному ArtifactStore. Модуль сам не вигадує receipt або фінансовий баланс.

Обмеження: це REST-знімки, а не готова WebSocket-підписка. Немає прив'язки до Host/Web, живого рахунка, наскрізного сценарію всіх агентів або доказу прибутковості. Публічний стакан WhiteBIT не включає RPI-заявки. `moneyPrec` не проголошується перевіреним кроком ціни. Ринки з оголошеним delisting у першому консервативному варіанті виключаються.

## Спільний наскрізний сценарій для воркерів

WhiteBIT public collector → ArtifactStore → існуючий market normalizer / MarketEvent → однаковий causal snapshot для математичних і LLM-спеціалістів → чинний specialist DAG / портфель / незалежний risk → чинні authority, reservation і SimulatedProvider → бухгалтерія та reconciliation → Host projection → доступний Web/Windows → пам'ять та незалежне оцінювання.

Один колектор може обслуговувати багато агентів. Ключі не роздавати агентам. Біржовий ліміт API контролювати централізовано. Десять ключів не створюють десять незалежних ринків або необмежену квоту.

## Конкретні власники робіт

**План 6, providers.** Прийняти collector після реального public HTTPS тесту. Завершити versioned instrument mapping для WHITEBIT/WHITEBIT_SPOT, tick/lot/fees, запис provenance. Додати офіційні WS bookTicker/quotes, ping, reconnect та resnapshot; мовчання незмінного ринку не вважати автоматично розривом. Не видавати websocket URL за реалізований транспорт. Private binding — окреме завдання лише після фактичної появи API-пари й дозволів, без реальних угод.

**План 3, runtime.** Реально зберігати raw artifacts, нормалізувати події, підтримувати один процес колектора, відновлення, freshness і read-only Host projection. Не створювати другу фінансову базу.

**План 2, команда агентів.** Споживати спільний версійований causal snapshot, а не робити по запиту до біржі від кожного агента. Обробляти NO_TRADE на невалідних/прострочених даних. Навчання — тільки на завершених outcome labels; сумнівні результати не просувати в ChampionRegistry.

**План 10, симуляція.** Використати існуючий PR #2389 та канонічний SimulatedProvider. Додати forward-режим на поточних public даних з віртуальним балансом, комісіями, прослизанням, мінімальними лотами й частковими/відхиленими виконаннями. Біржі не надсилати жодних віртуальних ордерів. Не називати synthetic-протокол реальним потоком без збереженого provenance.

**План 5, доступний інтерфейс.** У чинний web/src додати вибір джерела, ринку, bid/ask/spread, час і стан даних, вибір симуляційного рахунка, старт/пауза, заявки, комісії, баланс і причини рішення. Оновлення не забирає фокус. Частоту отримання даних і частоту мовлення налаштовувати окремо. Новий CLI — інструмент воркера, не заміна доступної кінцевої програми.

**План 4, безпека.** Не читати TOTP як API secret. Не класти жодних ключів у repo, журнал, prompt або HTML. Збереження credentials через чинний secret store; права читання/торгівлі/виведення розділені. Перевірити права на ринкові дані для майбутнього комерційного використання.

**План 7, кваліфікація.** Окремо підтвердити live public response, contract mapping, ArtifactStore, runtime, end-to-end симуляцію, UI/NVDA, restart і cross-provider тести. Нові 34 fixture-тести не замінюють цих доказів. На попередньому head #2393 CI research run 39062807810 зафіксував 985 тестів, 19 failures, 30 errors, 18 skipped; сім попередніх adapter/probe тестів пройшли. Потрібні scoped ремонти та точні повторні прогони, не декларація загального PASS.

## Приймання

WhiteBIT може бути першим наскрізним провайдером. Це НЕ доказ готовності всіх шести/десятків бірж, акцій, опціонів чи всього AutoTrade. Щонайменше другий незалежний провайдер потрібний для перевірки універсальності адаптерів. Старі DONE розділи не переписувати; нову можливість закрити після чинного source/CI/main readback та фактичного сценарію.
