# Доступний багатобіржовий термінал — критична продуктова оцінка

17.10.2026. Це дослідження й пропозиція, НЕ реалізований комерційний продукт, НЕ дозвіл на реальні угоди і НЕ видалення агентів AutoTrade.

## Продуктова теза

Користувач купує не обіцянку доходу, а доступне керування власним рахунком: самостійно дізнатися ціну, перевірити залишок, підготувати й підтвердити покупку, перевірити фактичне виконання, скасувати залишок заявки, розібрати комісії та ризик. Це зрозуміла цінність, але готовність аудиторії платити ще не виміряна.

Не стверджувати, що жодна біржа або торговельна програма доступна не є: потрібен сценарний аудит. Підтримка screen reader в окремому компоненті теж не доводить доступності всієї процедури реєстрації/торгівлі.

## Прямий конкурент, виявлений під час перевірки

Accessible Trading Terminal / Accessible Trader: https://accessibletrader.com/ і https://github.com/churst90/accessible-trade-terminal.

Поточний README заявляє 33 джерела даних, з них 16 торгових майданчиків, ручну live/paper торгівлю з озвученим переглядом заявки, клавіатуру, sonification, індикатори та налаштування повідомлень. Автор описує програму як безкоштовну, відкриту та підтримувану пожертвами. Це заяви й відкритий код автора, не наш незалежний NVDA/біржовий тест. ## Спільне ядро, два профілі

Зберегти одне фінансове/API ядро та два профілі: AutoTrade Autonomous і Accessible Manual Terminal. Не видаляти агентів з репозиторію і не форкати бухгалтерію. У ручному профілі autonomous strategy scheduling вимкнений; допоміжний агент не має власного інвестиційного мандата.

Повторно використовувати provider adapters, capability registry, точну арифметику, ризик, журнал заявок, reconciliation, secret store, Host API, stream/status transport, загальну Web/Windows оболонку. Перед повторним використанням перевірити фактичне приймання модулів: старий статус INTERNAL DONE не доводить завершення комерційного сценарію.

Розробити або істотно допрацювати майстер підключення, зрозумілий ручний order ticket, доступні заявки й комісії, вибір рахунка, керування мовленням, keyboard workflows, навчальний режим, багатомовні пояснення та користувацьку підтримку. Точний відсоток reuse без аудиту залежностей не обчислено.

## Як користувач працює

**Підключення.** Вибір підтримуваного провайдера й потрібної юридичної entity; секрети зберігаються локально зашифровано. Перевірка читання, статусу акаунта, ринків і прав. Якщо немає торгового дозволу, інтерфейс явно read-only. Без Withdraw/Transfer. Реєстрацію, KYC, CAPTCHA й видачу ключа повністю прибрати стороння програма не може.

**Огляд.** Рахунок, доступний залишок, ринки, bid/ask, спред, час даних, список спостереження, пошук. Чітко відрізняти USD/USDT, суму в quote currency і кількість активу. Перемикання рахунка скидає стару непідтверджену заявку або вимагає повторного перегляду; не переносить її мовчки.

**Покупка.** Стандартні label/input/select/radio: рахунок, ринок, купити/продати, ринкова/лімітна, кількість або бюджет, лімітна ціна, строк дії, підтримуваний захист. Перед відправленням — окремий огляд умов з оцінкою комісій та межами невизначеності. Після підтвердження — один ідемпотентний command у чинний Host. Показувати прийнято/частково виконано/виконано/скасовано/невідомо окремо.

**Помічник.** Запит «покажи ETH і підготуй лімітну покупку на 20 USDT» створює структуровану чернетку. Він не отримує ключі, не вигадує баланси, не надсилає наказ із тексту новини й не оголошує виконання без біржового підтвердження. Остаточне надсилання й повторний перегляд змінених умов — через доступний deterministic order ticket. За недоступності LLM ручна торгівля продовжує працювати.

**Повідомлення.** Отримання котирувань може бути швидким; читати вголос кожен tick для всіх ринків не потрібно. Окремі режими: на запит, не частіше N секунд, при зміні на X%, перетині межі; вільне мовлення не перебиває введення. Термінові фінансові події мають окремий канал. Тиша незмінного WS-ринку не тотожна відсутності зв'язку.

**Графіки.** Таблиця OHLCV, максимум/мінімум/зміна за період, клавіатурний крок по свічках, індикатори як текст; звук і Брайль як додаткові канали, не єдине джерело цифр.

## Межі «будь-якої біржі»

API-ключ не додає програмі новий конектор. Підтримка потрібна окремо для автентифікації, символів, одиниць, ордерів, мінімальних сум, ставок комісій, WebSocket, історії, permissions, entity/регіону й reconciliation. CCXT допомагає, але не доводить взаємозамінності API. 30–100 бірж — масштаб довгострокової підтримки, не проста кількість полів для ключів.

Початковий продуктовий експеримент: одна-дві повністю перевірені spot-інтеграції; потім ще одна, щоб підтвердити абстракцію. Деривативи/маржа/опціони — лише після окремого lifecycle, ризикового й UX приймання. Жодних обіцянок доступу на недозволений акаунту ринок.

## Комерційна перевірка — запропоновані, а не встановлені цифри

Провести 15–20 розмов із реально незрячими користувачами, які торгують або намагалися торгувати. Для 5–10 учасників — однакові завдання у конкурента й нашому прототипі: підключення, спостереження, купівля, скасування, часткове виконання, розрив мережі, комісії. Виміряти успіх без сторонньої допомоги, критичні помилки, час та повторне використання.

Тест цін — гіпотеза, наприклад 10–20 євро на місяць за підтримку/оновлення, а не готовий тариф чи доказ попиту. 200 користувачів × 15 євро = 3000 євро місячної виручки ДО податків, хостингу, підтримки, API, безпеки й юридичних витрат. Перевірити також B2B: доступний white-label інтерфейс для брокера або банку. У B2B можуть бути більші контракти, але дорожче інтегрування й довший цикл продажу.

Окремі перевірки: некастодіальна архітектура не автоматично звільняє від фінансового регулювання; модель приймання/передавання заявок і персональних рекомендацій потрібно юридично класифікувати до продажу. Для ЄС перевірити MiCA/MiFID за видами активів і реальною роллю оператора, GDPR, застосовність вимог доступності та ліцензії ринкових даних. Не подавати це як індивідуальний юридичний висновок.
