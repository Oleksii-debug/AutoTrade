# План прискорення AutoTrade — WhiteBIT, готові модулі, доступність, навчання

18.10.2026. Уточнення до всіх десяти чинних планів, не нове твердження про їхній DONE. Прочитані канонічні Drive-плани 1–10, GitHub status authority та поточний PR #2393; старі migration/DONE записи не підміняють актуальний виконаний тест.

## Обов'язкове правило вибору реалізації

Для кожного незавершеного модуля порівняти три шляхи: доробити свій, інтегрувати частину донора, замінити весь обмежений підмодуль. Врахувати лише майбутні витрати: адаптацію, дані, тести, безпеку, продуктивність, ліцензійні повідомлення, підтримку й відкат. Уже витрачені кредити не входять у рішення як аргумент зберігати код. Фіксувати вузький ADR з інтерфейсом, двома виконаними контрольними прикладами і конкретним рішенням. Коли повна заміна вигідніша — виконати її, зберігши міграцію та один фінансовий owner. Не будувати нескінченну обгортку довкола непридатного власного коду.

## Прив'язка до планів

План 1, фінанси: порівняти канонічний exact ledger/risk з готовими компонентами LEAN; не переносити прості float-paper-wallet з сторонніх ботів як фінансову істину. Перевірити одиниці WhiteBIT, комісію в конкретній валюті, мінімальні лоти, резерви, fills і reconciliation. Наявні фінансові інваріанти — критерії приймання будь-якої заміни, а не причина забороняти заміну.

План 2, агенти/навчання: використати наявний DAG; для конкретних прогалин порівняти Condor і TradingAgents. Пам'ять — FinMem/FinAgent як донори структури та retrieval. River — першочергова недорога модель online-learning. Avalanche — контроль забування. SB3/Gymnasium/VowpalWabbit — готові навчальні алгоритми. RD-Agent/Qlib/Optuna/DSPy — дослідження й оптимізація. Жодна назва бібліотеки не є доказом торгової переваги.

План 3, runtime: один collector, один потік нормалізованих подій для всієї команди; durable raw evidence, snapshots, restart, backpressure. DuckDB/Arrow — аналітика й обмін, OpenTelemetry — спостереження. Не створювати 15 однакових біржових з'єднань чи 15 копій великої моделі. Завершити Host projection для ціни, віку даних, режиму й стану рахунка.

План 4, безпека: слот `whitebit-primary`; власник підтвердив створення ключа. Секрет читати тільки із захищеного сховища, не GitHub/публічних логів/LLM. Перший крок — authenticated read без реальних заявок. Для донорів зберігати source SHA, notices і умови. Офіційний WhiteBIT SDK має MIT root LICENSE/pyproject та Apache згадку в README: зберегти відомості обох, не вигадувати власника коду. MCP із сотнею операцій не передавати моделі без allowlist.

План 5, доступність: whole-manual-subsystem comparison з `churst90/accessible-trade-terminal`. Перевірити order ticket, режим PAPER/LIVE, підтвердження, таблиці балансу/заявок, клавіатурну навігацію, керування мовленням і журнал. Можна переносити весь сумісний компонент; не вимагати миші, кольорів, графіків або drag/drop. Ручний профіль і автономна команда споживають одне ядро; агентів не вирізати з продукту лише заради ручного профілю.

План 6, провайдери: WhiteBIT — єдина активна нова інтеграція. Перевірити офіційний Python SDK та WhiteBit.Net і вибрати один головний транспорт для runtime. Уже повторно використаний точний upstream HMAC із MIT notices у read-only мосту; це не повна інтеграція SDK і не live account PASS. Далі main/trading balance, fees, history, REST/WS, reconnect, resnapshot та capability contract. Private reads відокремити від публічних market observations.

План 7, наука: дані навчання/валидації/незайманого holdout різні; timestamps і revisions причинні. Порівняння з cash/buy-and-hold/zero-LLM, витрати, просадки, uncertainty, множинний пошук, ablation кожного спеціаліста. Evidently працює headless та віддає числа/JSON, а не обов'язкову графічну панель. Результат FAIL/INCONCLUSIVE зберігати так само, як PASS.

План 8, інтеграція: завершити один сценарій public WhiteBIT → evidence → market events → agent/manual proposal → risk → simulated execution → ledger → UI → restart. Відокремити кодову наявність від виконаного end-to-end. У попередньому CI #2393 були помилки не тільки workflow-guard: fixtures adapter_version, owner_epoch, research distribution, learning labels. Потрібно звірити поточний main і відремонтувати причину, не приховати тест.

План 9, зовнішня перевірка: WhiteBIT account-binding/read track тепер має owner-confirmed credential availability; старе PARKED через відсутність створеного ключа більше не є достатньою причиною бездіяльності. Реальні торгові діагностики лишаються відкладеними: потрібні нове підтвердження суми, пари, рахунка, максимальної втрати/спреду, типу наказу та stop-condition. Ніякої обіцянки нульової втрати; withdrawal — окреме завдання, не частина buy/sell smoke-test.

План 10, симуляція: reuse PR #2389. Нові живі спостереження — WhiteBIT. Історичні сторонні дані маркувати справжнім джерелом, не видавати за WhiteBIT. Gymnasium wrapper має викликати той самий симулятор і його reward після комісій, а не заводити паралельний гаманець. Навчання й checkpoint повинні відновлюватися після перезапуску; модель-кандидат не може сама проголосити себе кращою.

## Порядок завершення

1. W01 фіксує slice/ownership і відновлює достовірну матрицю.
2. W02/W03 завершують private-read/public-data незалежно від відсутності депозиту.
3. W04–W07 зводять виконання, фінанси, runtime і симуляцію.
4. W08–W11 паралельно завершують команду, навчання й незалежну перевірку.
5. W12/W13 завершують ручний доступний UI та необов'язкового помічника.
6. W14 перевіряє source/dependency/secret supply-chain, W15 виконує точне наскрізне приймання і Windows handoff.

Кожен працює у своїй гілці й власному status-файлі. Спільні package/registry/host-contract зміни узгоджуються одним owner. Жодних 15 одночасних записів у main. Кожен завершений змістовний крок одразу отримує commit/тестовий доказ/статус; короткий звіт не замінює код.
